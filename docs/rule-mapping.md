# How a case's rules map to the registry

## Citations

A rule citation is a rule id, optionally qualified by a table row:

```text
SATIN-POOL-019            the rule
SATIN-KEY-005/step-12     row "step-12" of SATIN-KEY-005's table
```

A citation resolves against the rule registry of the case's spec, `specRef.descriptor` → the
descriptor → its `registry` digest → `rules.json` ([spec-identity.md](spec-identity.md)):

1. The id must be a key of the registry (`unknown-rule`).
2. A row qualifier must be one of the rule's `rows` (`unknown-rule-row`).
3. The rule must be `active` at that spec (`retired-rule`). A rule retired by a later spec does not
   affect a case pinned to an earlier one: each case resolves against its own registry.

The registry also gives the citation's text digest, so a review record can name the exact text an
expectation was approved against, and a consumer can detect that a new spec reworded it.

## What a case pins

`rules` lists the rules a case pins: the rules it was written to distinguish, at least one. It is
not every rule the expected values pass through: the intrinsic cost, the body's history, the two
pools, the ledgers, the receipt and the resource limits enter every transaction's expectation, and a
case pins them only when it was written to test them. Schema 1 also listed, per JSON Pointer into
`expected`, the rules whose evidence the value there was; schema 2 has no such lists (D-76), as an
Ethereum EEST fixture has none.

- The rules do not restrict comparison: every required group is compared in full, and a consumer
  reports a mismatch at its first differing path with the rules the case pins.
- Which rules a case pins is decided by its generator, by one rule applied to every case alike.
  The slice's is `tools/make_slice.py`'s `AREA_SCOPE`: a case pins the rules its derivation applied
  that are in its area's scope or that its definition names (D-76).
- Authoring intent (setup, triggering operation, boundary) belongs in `provenance`; the arithmetic
  and every rule a derivation applied are reproduced by the generator on demand
  (`tools/make_slice.py --explain <caseId>`), and reviewers check them against the pinned rule
  text.

## Coverage

From a manifest's cases and their registries:

- **Referenced-rule coverage**: active rules cited by at least one approved case, over all active
  in-scope rules.
- **Executed-rule coverage** of a consumer: the pinned rules of the cases that consumer ran and
  passed. A failure, `known-fail`, `unsupported` or `error` case contributes nothing, and a subset
  cannot claim coverage from cases outside it.

Imported Ethereum cases cite `SATIN-BASE-001` (the inherited base layer) and keep the upstream test
identity and specification reference in provenance. Historical specs need their own registries;
a Satin id is never cited for Rex6 behaviour.

## Reverse lookup

The generated [rule-to-case index](rule-index.md) lists the cases that cite each rule, sorted by
rule id and case id. It reads the gating and quarantined entries of `slice/index.json` and their
case files, preserves row-qualified citations, and links each case's own registry. Deliberately
wrong negative cases are excluded. A quarantined citation is not executed-rule coverage.

The final section lists rule ids no selected case cites. Its registry is the Satin snapshot with
the newest `source.committed` timestamp among those the cases reference (snapshot names break
same-time ties). The header names that snapshot; retired rules are labeled so they are not
mistaken for active coverage gaps. This lookup joins citations by rule id across snapshots:
an older case's citation does not prove that the newest wording has been tested.

Regenerate the file after changing the slice's cases or citations:

```bash
python3 -I tools/rule_index.py
python3 -I tools/rule_index.py --check
```

`--check` fails if the generated bytes differ or the index and case metadata disagree.
`tools/run-slice.sh` includes this check.
